### 1.1 Existing public review/publication pipeline (must be fed, not duplicated)

There is **no organization-specific publication shortcut to "refactor"** — an exhaustive grep for `PublicationSubmission`, `demot`, `promot` (as symbol-lifecycle verbs), and `withdrawn` (as a `SymbolRevision.lifecycle_state` value) across `backend/symgov_backend/` returns zero hits. §13 task 4's phrase "the current publication handoff for organization contributions" is best read as referring to the *generic* intake/publication pipeline below, which Stage 7 must extend to accept an organization-approved revision as input — not as evidence of existing organization-specific shortcut code that needs correcting.

- The existing pipeline is a case-management workflow built on `ReviewCase` (`backend/symgov_backend/models/schema.py:1463`: `source_entity_type`, `source_entity_id`, free-text `current_stage`, `owner_id`, `escalation_level`), `HumanReviewDecision` (`:1476`: `decision_code`, `from_stage`/`to_stage`, decider identity), `ReviewCaseAction` (`:1531`: agent/human action queue items keyed to a stage), and `PublicationApprovalTarget` (`:1495`: content-hash-pinned snapshot of exactly what was approved, unique per `review_decision_id`).
- `current_stage` values observed in code are pipeline-specific to image/drawing intake (`raster_split_review` — `publication_handoff.py:411`, `workspace.py:219`; `provenance_rights_review` — `tracy_operations.py:295`; `ready_for_publication_handoff` — gate checked in `validate_publication_handoff_authority`). **This is not the `submitted/triage/in_review/changes_requested/accepted/rejected/withdrawn` vocabulary FR-PUB-004 names** — that vocabulary does not exist as an implemented state machine anywhere yet, confirmed by grep.
- `backend/symgov_backend/publication_handoff.py` (1233 lines): `validate_publication_handoff_authority` (`:113-159`, requires `decision.decision_code == "approve"`, a current-decision race guard, and `review_case.current_stage == "ready_for_publication_handoff"`) and `execute_publication_handoff` (`:1051+`, locks via `lock_review_case_decision_authority`, queues a Rupert agent-queue item with `payload_json.standards_visibility="public"`).
- **Sole write site for `published_pages`/`pack_entries` today:** `backend/symgov_backend/runtime.py:2508` (`PublishedPage(...)`) and `:2537` (`PackEntry(...)`), inside Rupert's agent runtime, reached only through the above handoff.
- **Conclusion Stage 7 must design against:** a promotion request needs to produce (or adapt into) a `ReviewCase` that reaches `ready_for_publication_handoff` with an approving `HumanReviewDecision`, so `execute_publication_handoff` remains the single place that ever writes an `active` `published_pages`/`pack_entries` row. Whether Stage 7 creates a new dedicated organization-promotion model (mirroring I-10's own "does not overload... public `ReviewCase`" instruction for the *organization* side) that then opens/drives a `ReviewCase` at the appropriate stage, or reuses `ReviewCase`/`HumanReviewDecision` directly with `source_entity_type="organization_symbol_promotion"`, is an open decision — see §4 Q1.

### 1.3 Precedent for a dedicated promotion-request model (Stage 5's organization-review pattern)

Per I-10, Stage 7's promotion-request state machine should follow the same "dedicated submission/decision history, does not overload an existing lifecycle enum" pattern Stage 5 already used for organization approval, not invent a new shape:

- `OrganizationSymbolReviewSubmission` (`schema.py:855`) / `OrganizationSymbolReviewDecision` (`schema.py:891`) — dedicated submission/decision history for organization-internal approval.
- `backend/symgov_backend/organization_symbol_review.py` — `decide_submission` (`:104`), `set_organization_wide` (`:217`) with `_require_organization_wide_toggle_authority` (`:82`). `OrganizationSymbolReviewDecision.submission_id` is DB-unique (one decision per submission), and a deferred trigger `trg_governed_symbols_organization_wide_eligibility` (defined in `20260829_0033_organization_symbol_visibility.py`) enforces organization-wide eligibility only for an approved, closed decision — i.e., invariants are DB-enforced, not just application-checked.

### 1.4 The shared governed-symbol lock demotion must join (already exists — confirmed, not a gap)

`backend/symgov_backend/symbol_set_service.py` already takes a row lock on `GovernedSymbol` before every set-item write:

- `replace_items` (`:297`): `if session.get(GovernedSymbol, symbol_id, with_for_update=True) is None: raise HTTPException(404, ...)` — iterates `sorted(set(ids) | set(existing), key=str)` (sorted by UUID string, avoiding lock-order deadlocks) before touching `SymbolSetItem` rows.
- `copy_set` (`:520`): same `with_for_update=True` pattern.

**This is the exact serialization boundary §13 tasks 7–10 require** ("Make every Symbol Set item writer that adds or removes a public symbol lock the governed-symbol row first"; "Demotion begins as a request and impact preview... Lock the same governed-symbol row used by set-item writers"). No new lock primitive needs to be invented — demotion must take the identical `session.get(GovernedSymbol, symbol_id, with_for_update=True)` lock, in the same sorted-by-UUID order convention, before re-querying set-item references. The separate advisory-lock helper `publication_authority.lock_review_case_decision_authority` (`:9-24`, `pg_advisory_xact_lock`) is a different, unrelated lock (serializes `ReviewCase` decision execution) and is not the mechanism to reuse here, though `execute_publication_handoff`'s use of it is a second, independent serialization point promotion's final publish step will also pass through.

### 1.5 Step-up authentication — already implemented, reuse as-is

`require_recent_step_up` (`backend/symgov_backend/dependencies.py:586-610+`) checks `session_row.recent_step_up_at` against the I-25 10-minute (599s/600s boundary) window. Existing consumers: `routes/organizations.py` (6 sites), `routes/platform_admin.py` (9 sites). **No new step-up mechanism is needed** — Stage 7's demotion route(s) add `Depends(require_recent_step_up)` exactly like `routes/platform_admin.py`'s existing mutations.
