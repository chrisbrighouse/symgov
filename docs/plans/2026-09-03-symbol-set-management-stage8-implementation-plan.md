### 1.2 The response-shape problem: organization-private symbols have no page/pack

`published_symbol_row()` (`routes/published.py:88-151`) is not a thin filter away from organization-awareness — it **structurally cannot represent an organization-private symbol**:

- `published_symbol_display_id(row)` (`published_catalog.py:50-54`) raises `RuntimeError` if `row.catalog_symbol_id` is falsy. Organization-private symbols never have a `catalog_symbol_id` — Stage 7 established that allocation requires `visibility='public'` (`ck_governed_symbols_catalog_symbol_visibility_barrier`), and Stage 7's own promotion handoff is the only code path that ever calls the allocator.
- `effectiveDate`, `pageId`/`pageCode`/`pageTitle`, `packId`/`packCode`/`pack` are all sourced from `PUBLISHED_SYMBOLS_SQL`'s joins against `published_pages` / `publication_packs` / `pack_entries` — tables an organization-private symbol has no rows in at all, because only a promoted (public) symbol ever gets a `PublishedPage`/`PackEntry` row (Stage 7 `organization_promotion_handoff.py`).

**Confirmed via `python3 -m alembic heads` and direct code reading, not inferred:** an organization-private symbol — even one already `organization_wide=true` and org-review-approved — is just a `GovernedSymbol` + `SymbolRevision` row with no publication-pipeline artifacts whatsoever. Extending Catalog browsing to include it is therefore not a WHERE-clause change to the existing query; it requires a second, structurally different query (direct `GovernedSymbol`/`SymbolRevision` read, no page/pack join) whose results get merged with the public ones.

**Decision confirmed with Chris (§4 Q3):** the two result sets merge into **one list with a `source: "public" | "organization_private"` discriminator field** per item (mirroring `effective_palette.py`'s own `source` tagging convention already used for `"set"` vs. `"organization_wide"` entries), with page/pack fields `null` for organization-private entries and an org-appropriate substitute identifier (governed-symbol UUID or slug, not a `catalog_symbol_id`) used for the parts of the response that assume one. This fits `StandardsPage`'s existing behavior with the least rearchitecting — see §1.8.

### 1.3 Favourites — zero visibility filtering today, on the write and enrichment paths alike

`backend/symgov_backend/catalog_favourites.py` (74 lines, read in full):

- `load_favourite_symbol_ids(session, user_id, symbol_ids=None)` (`:17-30`) applies **no visibility filtering of any kind** — it returns every symbol ID a user has ever favourited, unconditionally, regardless of the caller's current session context.
- `add_catalog_favourite`/`remove_catalog_favourite` (`:33-74`) take no visibility check on write either.
- Six call sites, all in `routes/published.py`: `:388` (bare-ID list, `GET /favourites`), `:398`/`:423` (add/remove path resolution), `:414` (remove-conflict check against already-favourited IDs), `:467` (enrichment join in `list_published_symbols`) — plus two more (`get_published_symbol`, comment/detail enrichment) not yet audited line-by-line in this planning pass; the implementing work package must re-grep at implementation time rather than trust this count as final.
- Stage 7's own `test_hannah_and_whitney_background_readers_exclude_the_demoted_symbol` sibling case already proved, for **demotion** specifically, the "bare ID retained, no detail leak" pattern: a demoted symbol's raw ID survives in `GET /favourites`'s unenriched list, but the enriched, joined view (`list_published_symbols`) silently excludes it because the join against `PUBLISHED_SYMBOLS_SQL` naturally drops it. **Stage 8 must generalize this same pattern to organization boundaries**, and make it *session-context-sensitive*, not just lifecycle-sensitive: a symbol visible while org A is active must vanish from enrichment the instant the same user is in org B's session or personal mode — not just when demoted. This is a materially new axis of variation `load_favourite_symbol_ids` was never designed for.
- `CatalogFavourite` (`models/schema.py:525-537`) is schema-minimal — `user_id`/`symbol_id` composite primary key, both foreign keys, no visibility columns. **Confirmed no migration is needed for Favourites** — this matches the spec's own §8.1 statement ("No structural change required except tenant-aware visibility validation") exactly; the fix is query-time, not schema.
- **`GET /favourites`'s bare-ID list must keep listing stale/hidden IDs unchanged** — per §14 ("historical rows remain for restoration/audit and may be safely removed by their owning user without exposing hidden symbol details") and per FR-CTX-008 — this stage only needs to make the *enriched* views context-sensitive, not the raw favourite-ID ledger itself.

### 1.4 Effective palette (Stage 6) — the reusable organization-wide query shape

`backend/symgov_backend/effective_palette.py` (read in full) already computes exactly the organization-private subset Stage 8 needs, in `_organization_wide_entries` (`:102-124`): `owner_organization_id == <active org>`, `visibility == 'organization_private'`, `organization_wide.is_(True)`, ordered by canonical name. No lifecycle-state filter is applied beyond that — `current_revision_id` is used directly, which is Stage 6's existing, already-shipped behavior; Stage 8 does not need to (and should not) change this query's own semantics, only reuse its shape for the Catalog-browsing surface.

**This is now the confirmed scope boundary (§4 Q2):** Stage 8's organization-private Catalog visibility is `organization_wide=true` symbols only — the one path that actually exists and is exercised in production code today.

### 1.5 I-09's "set-only private symbol" category was never implemented — treated as superseded

The decision addendum's I-09 states: *"Organization-private symbols are either set-only or organization-wide; set-only private symbols are returned only through eligible set membership."* This implies a category of organization-private symbol that a Symbol Set can reference directly without being `organization_wide=true`.

**Confirmed by direct code reading, not inferred:** `symbol_set_service.py:329-330` — `replace_items` rejects any *new* `SymbolSetItem` whose governed symbol is not in `current_public_symbols` (public, published, eligible) at write time: `"Every new item must be currently eligible in the public Catalog."` **An organization-private symbol cannot be added to a Symbol Set as an item at all, today.** `effective_palette.py`'s own header docstring (`:23-35`) independently confirms this as a deliberate invariant: the two halves of its union (set items vs. organization-wide) are "disjoint by construction… a symbol cannot flow from one source into the other," because `SymbolSetItem` can only ever reference a `visibility='public'` symbol.

I-09 therefore describes a mechanism Stage 6 never built. **Decision confirmed with Chris (§4 Q2-addendum):** treat I-09's "set-only" half as superseded by Stage 6's actual, narrower implementation. Stage 8 does not build the missing set-only mechanism (that would be new Symbol Set write-path/eligibility work, well outside a Catalog/favourites/UI read-integration stage per §14's own framing) — organization-wide is the only organization-private path Stage 8 needs to surface.

### 1.6 Canonical resolver — structurally public-only, not a visibility gap to fix

`catalog_symbol_resolution.py`'s `resolve_catalog_symbol` (`:134+`) has four branches (canonical/uuid/slug/historical_alias), all four gated on `catalog_symbol_id IS NOT NULL` — confirmed by Stage 7's own WP7.5/WP7.7 audit (already proved in this repository's history). Since organization-private symbols never have a `catalog_symbol_id` (§1.2), this resolver **structurally cannot resolve one today** — this is not a bypass risk to close, it is the reason a *separate*, additive resolution path is needed for organization-private detail/asset lookups (by raw governed-symbol UUID, scoped to the caller's own active organization). §14's "ensure canonical resolver aliases cannot bypass visibility" reads as a don't-regress instruction for the existing public-symbol paths — Stage 8 must not modify `resolve_catalog_symbol` itself, only add alongside it.

### 1.7 What already exists for organization-private symbol listing (a different, non-integrated surface)

`routes/organization_symbols.py`'s `list_organization_symbol_drafts` (`:174-184`, backed by `organization_symbol_drafts.py`'s `list_drafts`/`get_draft`, `:201-217`) already returns an authorized org's own symbols (drafts through approved/withdrawn) with role-scoped visibility (own drafts for contributors, everything for admin/reviewer, per spec §9.1) — query pattern: `owner_organization_id == organization_id`, `visibility == 'organization_private'`, role-gated further by `owner_id` for non-privileged callers.

This is a **separate admin-style CRUD listing**, not integrated into a unified Catalog browsing UI with public results, and not scoped to `organization_wide=true` — it shows every draft-state symbol, not just the approved/organization-wide subset a Catalog browsing surface should show. Stage 8's job per §11.5 is to merge the *browsable* (organization-wide, already-approved) subset into one experience with badges and a scope toggle — not to build a new listing endpoint from scratch, and not to expose in-review drafts through Catalog browsing.

### 1.8 Frontend: "Standards" and "Catalog" are the same surface (confirmed with Chris)

`App.jsx:770`: the left-rail nav item routed to `/standards` is labeled `"Catalog"` (`<RailNavLink to="/standards" label="Catalog" ... icon="catalog" />`). **Chris confirmed (§4 Q1) this is intentional, current product terminology, not a naming collision to resolve**: Standards View was renamed to "Catalog" as the consumer-facing area where users browse, search, view, and download symbols. `StandardsPage()` (`App.jsx:953+`) is therefore the correct, single mount point for Stage 8's org-aware Catalog experience — not a new Workspace-mounted surface, and not a new dedicated route.

It calls `GET /published/symbols` via `fetchPublishedSymbols()` (`api.js:1498-1499`) — confirmed to have **no server-side pagination today**; `list_published_symbols` (`published.py:427-477`) returns the full unfiltered `items` array, and all filtering/sorting/faceting happens client-side. This is directly relevant to the §1.2 response-shape decision: a merged flat array with a `source` discriminator fits this existing client-side model far more naturally than either alternative response shape would have.

**WP8.3 implementation note (2026-09-03):**

*Scope correction, found while implementing, not guessed in advance:* the original plan text (§2 above, now rewritten) assumed `load_favourite_symbol_ids` needed a new session-context parameter threaded through its "six-plus call sites" so *enrichment* would exclude a cross-organization stale favourite. Auditing all six real call sites in `routes/published.py` found this premise didn't hold:

- `list_published_symbols` (WP8.1, §1.2) and `get_published_symbol` (WP8.2, §1.6) both call `load_favourite_symbol_ids` bounded to exactly the `symbol_ids` already present in that response's own already-tenant-scoped result — a different organization's private symbol structurally cannot appear in that bounded list to begin with (its own query never returns it), so there was never anything for a session-context parameter to filter out at these two sites.
- `get_published_page` is public-only by construction (backed by `PUBLISHED_SYMBOLS_SQL` directly — pages only exist for promoted symbols) — same reasoning, no organization-private symbol can ever reach it.
- `GET /favourites` (the bare ID list) and the "already-a-favourite" fast path inside `DELETE /favourites/{symbol_ref}` are **deliberately unscoped by design**, per plan §1.3/FR-CTX-008 ("historical rows remain... may be safely removed by their owning user without exposing hidden symbol details") — adding scoping there would be a regression, not a fix.
- The **real, previously-unnoticed gap** was `PUT /favourites/{symbol_ref}` (add): it only ever resolved `symbol_ref` via the public-only `_load_published_symbol_row`, meaning **an organization-private symbol could never be favourited at all** — not a leak, the opposite defect (a missing feature blocking §14/§11.5's "Favorites remain keyed to user and governed symbol" / "personal shortcuts" requirement for organization-private symbols).

Fixed by routing both `add_current_user_catalog_favourite` and (for its own non-fast-path resolution fallback only, for consistency) `remove_current_user_catalog_favourite` through the same `_load_symbol_for_detail` helper WP8.2 built — additive, organization-scoped-by-construction resolution, no change to `load_favourite_symbol_ids` itself, no change to any of the four enrichment/bare-list call sites reasoned about above.

Per the Stage 5-7 precedent: cross-organization visibility leaks are exactly the class of bug that cannot be trusted to SQLite or to reasoning-from-the-code alone. Every acceptance-bar test in WP8.4 must run against the real disposable-Postgres harness, proving — not assuming — that the same URL under two different organization-bound sessions never returns the other organization's private data, and that personal-mode/API-key behavior is bit-for-bit unchanged. Full portable backend suite (`scripts/test-backend.sh`) and the external/Postgres suite must both be re-run and reported (pass/fail counts, explicit confirmation of which pre-existing failures — if any — were independently reproduced against pre-Stage-8 `main`) before any work package is reported complete, following the WP6.1/WP6.6/WP7.7 precedent of never attributing a pre-existing failure to new work without independent reproduction.
