### 1.1 No usage-telemetry or reputation infrastructure exists today — fully greenfield

Grepped migrations and `backend/symgov_backend/models/schema.py` for `usage`, `telemetry`, `analytics`, `event_type`, `ContributionEvent`, `badge`: nothing matching Stage 9's own scope exists. Two adjacent-but-distinct tables already exist and must **not** be repurposed, per I-13's explicit instruction and the spec's own §13.3 ("Separate operational logs, product analytics, security signals and contribution reputation"):

- `CatalogApiUsageEvent` (`schema.py:570-598`, migration `20260710_0019_catalog_api_usage_events.py`) — API-key traffic only (`routes/catalog.py`'s surface). Fields: `api_key_id`, `customer_name_snapshot`, `integration_name_snapshot`, `scope_used`, `method`, `path`, `route_name`, `status_code`, `latency_ms`, `request_id`, `query_text`, `symbol_ref`, `result_count`, `ed_query_type`, `user_agent`, `client_ip_hash`, `application_name`, `application_version`, `created_at`. I-13: "Keep `CatalogApiUsageEvent` for API-key traffic. Add a separate server-derived authenticated browser/product-usage event domain."
- `LLMUsageEvent` (`schema.py:601+`, migration `20260730_0025_llm_usage_events.py`) — LLM call cost/latency tracking, structurally unrelated to product usage but the **best structural precedent to imitate**: a frozen, `CheckConstraint`-enforced enum vocabulary for every categorical column (`environment`, `use_case`, `service_name`, `provider`, `status`, `initiator_kind`, etc.), covering indexes on `(dimension, occurred_at)` pairs, a JSONB escape-hatch column (`other_usage_json`) with its own `jsonb_typeof(...) = 'object'` constraint, and cross-column provenance constraints (e.g. `llm_usage_events_cost_provenance`). This is the pattern Stage 9's new product-usage event table should follow, not `AuditEvent`'s looser shape.
- `AuditEvent` (`schema.py:796-805`) — generic entity-mutation audit log: `id, entity_type, entity_id, action, actor_id (nullable FK users), payload_json (JSONB), created_at`. Used across ~15 files for governance mutations (demotion, promotion, review decisions, etc.). This is *audit*, not *analytics* — I-13 and spec §13.3 both require these stay separate domains. Stage 9 must not repurpose `AuditEvent` rows for browse/search/preview volume, and must not stop emitting `AuditEvent` rows for governance mutations that already emit them — the new product-usage event table is additive, emitted *alongside* the existing audit trail for governance events, and standalone for browse-only events that have no `AuditEvent` counterpart today (preview, download, search, Favorite, context/set selection).

### 1.2 Spec's required event catalog is large; the scoring/reputation model is explicitly NOT all v1 scope

Appendix B (spec lines 966-995) lists ~25 canonical event names spanning session start, organization/project/set lifecycle, context resolution, preview/download/Favorite, private-draft/review/promotion/demotion, and agent-finding lifecycle (the last of these is Stage 10's own domain, not Stage 9's — Stage 9 should emit `contribution_awarded`/`contribution_reversed` and the governance-adjacent events already relevant to reputation, but agent-finding events belong to whichever stage actually builds `AgentFinding`/`AgentConfiguration`, i.e. Stage 10, per the programme plan's own dependency ordering).

**I-14 is the load-bearing scope boundary for reputation:** *"Initial reputation consists of auditable contribution/review counts and badges. Weighted points and commercial benefits require a later versioned policy accepted by Chris. Reputation never grants authority."* This directly narrows spec §12.1's illustrative points table (+100/+40/+20/+5/+25) — that table is not itself an accepted v1 scoring policy; it is the spec's own "illustrative" placeholder (§12.1's column header literally reads "Illustrative points"), and O1/I-14 both defer the real policy. **Read literally, this means Stage 9 v1 should build the append-only `ContributionEvent` ledger and count-based badges, but should not activate a live weighted-points display or leaderboard ranking derived from those points**, until Chris accepts a versioned scoring policy separately. §4 Q2 below asks Chris to confirm this reading before any schema/service work begins, since it's the single decision most likely to reshape `ContributionEvent`'s own column set (whether `points` is even populated in v1, or reserved-but-unused pending the later policy).

### 1.3 "Server-derived" and "same transaction" are the load-bearing integrity requirements

Programme plan line 916: *"Derive principal/context server-side and emit in the same transaction for governance mutations; low-value browse events may use a bounded durable ingestion path with documented loss behavior."* This is two different reliability tiers, not one:

- **Governance-mutation events** (organization review decision, promotion, demotion, role/capability change, project/set create-update-archive-select, icon uploaded/removed) must be emitted transactionally, in the same database transaction as the mutation itself. **Correction (found while starting WP9.2, 2026-09-04 resumed session): this section's "project/set lifecycle has no audit trail today" claim was wrong.** `project_service.py`, `symbol_set_service.py`, and `symbol_context_service.py` all share a working `audit()` helper (wrapping `AuditEvent`) already called at every project/set mutation and selection site; `organization_service.py` has its own `_emit_audit()` helper already wired into every icon/role/capability/platform-admin mutation. There is no audit-trail gap to close — WP9.2's job is purely additive `session.add(ProductUsageEvent(...))` calls alongside these already-existing `audit(...)`/`_emit_audit(...)` calls (and alongside the two `AuditEvent`s `symbol_demotion.py` already adds), not new `AuditEvent` emission anywhere. §4 Q4 is corrected accordingly.
- **Low-value browse events** (preview, search, zero-result search, context resolution, symbol download-without-mutation) explicitly may use "a bounded durable ingestion path with documented loss behavior" — i.e., best-effort, not transactionally guaranteed. This is architecturally significant: it is the one place in this stage where a genuinely new piece of infrastructure (an async/buffered ingestion path) is plausible, rather than a straightforward synchronous insert. **This repository has no existing async task queue or background worker infrastructure for anything resembling this** (confirmed: no Celery/RQ/arq/similar dependency in `backend/requirations.txt`, no background-worker process alongside the FastAPI app) — introducing one would be a materially larger architectural decision than anything Stage 5-8 needed, and is exactly the kind of choice that needs Chris's explicit sign-off before any code is written (§4 Q5).

### 1.4 No dashboard-building precedent exists on the frontend; no chart library is installed

`OrganizationAdminPage.js` and `PlatformAdminPage.js` (grepped, not fully read in this pass) use plain React (`createElement`, hooks) with hand-rolled stat blocks (`dt`/`dd` pairs) — no chart/visualization library. Confirmed via `package.json`: no `recharts`, `d3`, `victory`, `chart.js`, or similar dependency exists anywhere in `frontend/`. Any Stage 9 dashboard UI is genuinely greenfield on both axes: the data-fetching pattern (existing admin pages call REST endpoints directly with hooks — a pattern to follow, not a gap) and any chart rendering (nothing to reuse; a real choice between hand-rolled stat tiles matching the existing visual language, per `CLAUDE.md`'s "prefer the existing visual language," versus introducing a new charting dependency, which `CLAUDE.md`'s validation section requires Chris's separate explicit approval for as a "new npm dependency"). §4 Q6 asks this directly rather than assuming either answer.

### 1.5 Retention periods and aggregation thresholds are unspecified numbers, not just unspecified policy

Spec §13.3: *"Support retention policies and aggregate reporting thresholds."* This is a requirement to have a documented, enforced number, not a design pattern to implement generically — and no number appears anywhere in the spec, decision addendum, or `CLAUDE.md`. Per `CLAUDE.md`'s "do not invent production metrics, workflow states, or backend contracts," Stage 9 must not invent a retention period (e.g. "90 days") or a minimum-aggregation threshold (e.g. "suppress any aggregate cell representing fewer than 5 distinct users") without Chris confirming the actual number — these are real business/privacy decisions, not implementation details. §4 Q7.

### 1.6 Anti-gaming rules are qualitative; "flag suspicious linked accounts" has no defined detection rule

Spec §12.4 lists five anti-gaming principles (no credit for raw uploads/likes/self-downloads/same-org-only activity, dedupe before review, hide points from reviewers, append-only + reversal corrections, rate-limit + flag suspicious linked accounts). The first four translate directly into concrete, testable rules on the `ContributionEvent` ledger and its awarding service. The fifth ("flag suspicious linked accounts or organizations without automatic punishment," per the programme plan's own added qualifier) has no defined detection heuristic anywhere in the source documents — this is real design work, not a lookup, and risks inventing a fabricated "fraud detection" mechanism if not scoped precisely. §4 Q8.

### 1.7 Existing pattern for "separate domain, frozen vocabulary" tables to imitate structurally

`LLMUsageEvent`'s own `__table_args__` (schema.py:605-634) is the concrete template for how this repository already expresses "an append-only event table with a frozen, schema-validated categorical vocabulary" — every enum-shaped column gets its own named `CheckConstraint`, cross-column provenance rules get their own constraint, and a JSONB escape hatch (`other_usage_json`) is itself constrained to `jsonb_typeof(...) = 'object'` rather than left as an unconstrained free-form blob. Stage 9's new product-usage event table (and `ContributionEvent`) should mirror this exactly: a single `event_type` column constrained to the frozen Appendix-B-derived vocabulary (minus Stage 10's agent-finding events, per §1.2), rather than a free-text column.

This is a tested, callable unit only, exactly matching this package's own "schema (and its supporting retention mechanism) only, no emission wiring yet" scope.

## 4. Decisions confirmed with Chris (2026-09-03, resumed session)

Unlike Stage 8's four decisions, these were genuine product/architecture choices this stage's own source documents left open — guessing wrong on any of them would have meant rebuilding schema or a whole service tier, not just relabeling a field. All nine are now resolved; §2's work-package sequence above has been finalized against these answers (see the per-package notes there).

1. **Q1 — Event catalog scope for v1: narrower core subset first.** WP9.1 builds only the browse-facing subset of Appendix B's catalog (session/context/preview/download/Favorite/set-selection) in its frozen `CheckConstraint` vocabulary; governance-lifecycle events (organization review, promotion, demotion, project/set lifecycle, icon, role/capability changes) are added in a follow-up extension to the same constraint once WP9.2 needs them, not invented ahead of need. Rationale: additive extension of a `CheckConstraint` is cheap; narrowing one after other code depends on it is expensive.
2. **Q2 — Points column: omitted entirely for v1.** `ContributionEvent` (WP9.5) will not have a `points` column at all until a real, versioned scoring policy is accepted separately (I-14/O1). No dead/unpopulated column, no premature commitment to the spec's illustrative §12.1 numbers. Adding the column later is its own small additive migration once a policy exists.
3. **Q3 — Badge set for v1: three well-defined badges only.** WP9.5 builds First Contribution, Contributor Organization, and Community Partner — each has an unambiguous trigger derivable from the `ContributionEvent` ledger alone. Multi-Discipline Contributor and Metadata Improver are deferred until Chris defines their exact thresholds (a discipline-count number; a precise definition of "metadata improvement" versus a new symbol) — building them now would mean inventing a heuristic, which `CLAUDE.md` prohibits.
4. **Q4 — Project/set lifecycle audit gap: superseded, no gap exists.** This question was resolved to "close it in WP9.2," but starting WP9.2's implementation found the premise was wrong: `project_service.py`/`symbol_set_service.py`/`symbol_context_service.py` already share a working `audit()` helper called at every project/set create/update/archive/select site, and `organization_service.py` has its own `_emit_audit()` doing the same for icon/role/capability/platform-admin actions. WP9.2 adds only `ProductUsageEvent` rows alongside these existing calls — no new `AuditEvent` emission anywhere. See the corrected §1.3.
5. **Q5 — Browse-event ingestion: synchronous insert.** WP9.3 inserts `ProductUsageEvent` rows synchronously on the same request thread for preview/download/search/context events — no new async/worker infrastructure. Simplest and lowest-risk; accepted trade-off is minor added latency on browse-facing endpoints, not a "bounded durable" queue in the spec's most literal sense.
6. **Q6 — Dashboard rendering: hand-rolled stat tiles.** WP9.7 matches `OrganizationAdminPage.js`'s existing `dt`/`dd` stat-block convention — no new charting dependency, consistent with the existing visual language and `CLAUDE.md`'s validation-section bar on new npm dependencies.
7. **Q7/Q7b — Retention and aggregation threshold: confirmed numbers.** Raw `ProductUsageEvent`/`ContributionEvent` rows: 90-day retention, after which raw rows are purged; rolled-up aggregate counts are kept indefinitely for dashboards/trends. Minimum aggregation threshold: an Organization Admin or Platform Admin dashboard must suppress or group any aggregate cell backed by fewer than 3 distinct users, to prevent an "aggregate of one" from revealing an individual's behavior. Both numbers gate WP9.4's dashboard-query design and WP9.9's audit checks directly — WP9.1/WP9.4 must implement the purge job and the threshold enforcement to these exact numbers, not placeholders.
8. **Q8 — "Suspicious linked accounts" detection: scoped out of v1.** WP9.6 does not build this specific anti-gaming control — no Chris-confirmed detection signal exists to build against, and inventing one would violate `CLAUDE.md`'s prohibition on inventing workflow states/contracts. The other four §12.4 anti-gaming rules (no credit for uploads/likes/self-downloads/same-org-only, dedupe before review, hide points from reviewers — moot given Q2's no-points decision, so this reduces to "hide reputation detail from reviewers during review" — append-only + reversal corrections, rate-limiting) remain in WP9.6's scope. Revisit the suspicious-account control once a real signal is defined.
9. **Q9 — Opt-in leaderboard: deferred.** WP9.8 builds individual private stats and organization-only public attribution (badges/counts) but does not build the opt-in leaderboard in this stage — badges and stats alone already satisfy AC-22 and the spec's core dashboard requirements. The leaderboard is recorded as an explicitly out-of-scope nice-to-have for a later stage/patch, not silently dropped.
10. **Q10 — Rollup refresh: periodic batch, not synchronous-incremental (confirmed 2026-09-04, WP9.4 planning).** Keeping aggregate rollups indefinitely past the 90-day raw-row purge (Q7) requires a new persisted `product_usage_daily_rollups` table, which wasn't itself decided in the original Q1-Q9 round — this was a genuine architecture fork found while starting WP9.4, not a pre-answered question. Chris confirmed a standalone, callable batch-refresh function (`refresh_product_usage_rollups`, mirroring WP9.1's own unscheduled `purge_expired_product_usage_events`) over touching every already-committed WP9.2/9.3 emission call site again to increment rollup counters synchronously — simpler, and avoids a subtle correctness risk in incrementally tracking `distinct_user_count` (the exact figure the 3-distinct-user threshold depends on) without re-scanning raw rows. Like the purge job, this refresh is not wired to any scheduler; production scheduling of either job is a separate deployment/operations decision requiring its own explicit approval, and must run the refresh before any purge that would delete rows it hasn't yet aggregated.

### 4a. Further decisions confirmed with Chris specifically for WP9.5 (2026-09-04)

Spec §12.2 names all three in-scope badges as "Organization badges" but gives no trigger definition for any of them, and §12.4's "reversal entries" has no defined shape — genuinely open design questions this session's own earlier research (code inspection of `organization_symbol_review.py`/`organization_promotion_handoff.py`/`symbol_demotion.py`) could narrow but not resolve alone. Four further questions were put to Chris before any WP9.5 schema/code was written:

- **Q11 — First Contribution vs. Contributor Organization: same trigger, two records.** Both badges fire at the exact same moment — an organization's first-ever accepted contribution — and are written together as two separate `OrganizationBadge` rows. No separate "sustained activity" threshold for Contributor Organization (which would have meant inventing an unconfirmed number).
- **Q12 — Ledger trigger: public promotion acceptance only.** A `ContributionEvent` row (`contribution_awarded`) is written only when `organization_promotion_handoff.execute_organization_promotion_handoff` accepts a symbol's public promotion — organization-review approval alone (which only reaches organization-private visibility, never public) does not write a ledger row. Matches spec's own framing of "contribution" as public-catalog attribution.
- **Q13 — Community Partner: deferred, alongside the already-deferred Multi-Discipline Contributor/Metadata Improver.** No infrastructure exists anywhere in this repository linking a public symbol's owning organization to the distinct *other* organizations consuming it (`ProductUsageEvent`/its rollups record the viewing organization's own session, not the symbol owner's) — building a cross-org-adoption heuristic now would mean inventing one, which `CLAUDE.md` prohibits. WP9.5 computes exactly two badges (First Contribution, Contributor Organization), not the three §4 Q3 originally scoped; Community Partner needs its own future adoption-tracking design before it can be built.
- **Q14 — Reversal shape: a new row with a `reversed_event_id` back-reference, original stays immutable.** A `contribution_reversed` row is a fresh, independent `ContributionEvent` row (own copy of every dimension column) carrying `reversed_event_id` pointing at the original award row's id — not an in-place mutation of the original, mirroring WP9.1's own append-only/immutable-via-trigger precedent for this stage's other tables.

### 4b. Further decisions confirmed with Chris specifically for WP9.6 (2026-09-04)

Re-reading spec §12.4 against WP9.5's own already-shipped design (before assuming the original WP9.6 plan-doc line was still literally accurate) found two of the five anti-gaming rules already structurally satisfied and one genuine, previously undocumented gap (`promotion_requests._require_reviewer_authority`'s reviewer-authority check is deliberately global, not organization-scoped — a documented Stage 7 policy choice, not a bug). The remaining two rules ("dedupe before review," "rate-limit repeated submissions") were confirmed to need genuinely new design work, not verification. Five questions were put to Chris before any WP9.6 code was written:

- **Q15 — Same-organization self-review: block it.** A reviewer who is also an active member of the promotion's own submitting organization may not accept that organization's promotion, even though reviewer authority is otherwise deliberately global (Stage 7's own documented design, left unchanged for every other organization). Enforced in `execute_organization_promotion_handoff`, defense-in-depth in the service layer.
- **Q16 — Dedupe fields: `canonical_name` + `category` + `discipline`.** Compared only against existing *public* `GovernedSymbol` rows. Not the fuller "+ standards links" option — standards-link data is not reliably populated at submission time in this repository yet.
- **Q17 — Dedupe action: flag, don't block.** A detected duplicate does not stop the submission; it is recorded informationally on the `PromotionRequest` row.
- **Q18 — Rate limit: 10 promotion submissions per organization per rolling 7 days.** Counts every real submission regardless of its later status, not just currently-open ones. No number existed anywhere in the spec/decision addendum/plan doc; per `CLAUDE.md` this could not be invented.
- **Q19 — Duplicate-flag surface: extend the existing reviewer-facing `PromotionRequestResponse`, not DB-only.** There is no dedicated workspace review-case renderer for `organization_symbol_promotion` cases at all (confirmed by grep — a known, already-documented gap from WP7.3), so the one real surface a reviewer sees a promotion request's own detail through today is `PromotionRequestResponse` (returned by `open_organization_symbol_promotion_review`). Chris confirmed extending that response with the duplicate-flag fields now, rather than leaving the flag queryable-but-invisible pending a future frontend work package.

## 5. Regression standard (carried forward from Stage 5-8, expected to apply unchanged)

Per the Stage 5-8 precedent: any cross-tenant or cross-user data-visibility question in this stage's own domain (a different organization's usage data, another user's individual contribution/reputation detail) is exactly the class of bug that cannot be trusted to SQLite or to reasoning-from-the-code alone, and must be proven against the real disposable-Postgres harness this repository already uses for every prior stage's cross-tenant tests. This stage additionally introduces a privacy axis Stage 5-8 didn't need to prove as rigorously (individual-user behavioral data, not just organization-scoped governance state) — WP9.9's audit should treat "can an Organization Admin see another individual's raw behavior beyond an aggregate threshold" with the same rigor Stage 7/8 gave cross-tenant leaks.
