### 1.1 `AgentConfiguration`/`AgentFinding` are fully greenfield; a different, unrelated agent-runner domain already exists and must not be repurposed

Confirmed this session: `grep -rn "AgentConfiguration|AgentFinding" backend/symgov_backend/models/` returns nothing at all. Stage 10's two new entities do not exist in any form today.

This repository already has a large, working, **unrelated** agent-runner system for its own symbol-intake/curation/review pipeline: `AgentDefinition`, `AgentQueueItem`, `AgentFeedbackEvent`, `AgentRun`, `AgentOutputArtifact` (all in `backend/symgov_backend/models/schema.py`), backing the existing Scott/Vlad/Tracy/Daisy/Libby/Rupert/Ed/Hannah/Reggie/Whitney pipeline (seeded via `manage_symgov.py seed-agent-definitions`, documented in `backend/README.md`'s "Current runner bridge notes"). Per I-21's own text: *"Existing `AgentDefinition.model` is a compatibility/runtime projection; the legacy OpenClaw manifest cannot override Hermes after cutover."* Stage 10 must not repurpose `AgentDefinition`/`AgentQueueItem` for its own scope, and must not assume `AgentDefinition.model`'s flat text column is how `AgentConfiguration.model_alias` resolution should work — I-21 explicitly rejects that. This mirrors Stage 9's own WP9.1 lesson (don't repurpose `CatalogApiUsageEvent`/`AuditEvent` for a new, structurally-distinct domain) — two adjacent-but-distinct tables must not be conflated.

### 1.2 The `organization_agents_enabled` feature flag already exists — Stage 10 builds behind it, does not invent a new one

Confirmed this session: `backend/symgov_backend/settings.py:181` already defines `organization_agents_enabled` (env var `SYMGOV_ORGANIZATION_AGENTS_ENABLED`, same boolean-parse pattern as the other I-20 flags), and `backend/symgov_backend/routes/auth.py:111` already exposes it on `/auth/me` as `organizationAgentsEnabled` (gated additionally on `organizations_enabled`). Stage 10's schema/service/route work gates on this existing flag; it does not need a new flag name invented.

### 1.6 Deterministic-first is the programme plan's own explicit framing, not just an inference from FR-AGT-009

### 1.7 O4 (logical-capability-to-real-Hermes-agent mapping) is a genuine open architecture question, not a code-only decision

O4 (already accepted as a *contract*, not a closed implementation): *"Keep `Organization Steward` and `Platform Governance` as logical capability names; map them to existing or new Hermes agents during implementation."* FR-AGT-010 hints Hermes "may route agent findings to existing support/issue capabilities such as Ed or Alfi" — and `ed` already exists as a live agent id in the (non-git, read-only-inspected) manifest found in §1.4 — but nothing in this repository commits to Ed specifically being reused versus new Hermes agent entries being created for Organization Steward/Platform Governance themselves. Per this repository's own live-infrastructure boundary (`CLAUDE.md`: no deployment/live-mutation without explicit approval; the manifest in §1.4 sits outside this git repository entirely), actually creating/binding a new Hermes agent identity is very plausibly outside this repository's own commits' reach. This may mean Stage 10's own code-side deliverable stops at "the database/API/UI side is ready to be pointed at a real Hermes agent identity once one exists," rather than this session wiring up the live Hermes side itself. See §4 Q5.

### 1.8 "Cadence/trigger records" and "approved platform reports" are both unresolved concrete-mechanism questions

The programme plan's §16 body requires "explicit cadence/trigger records" for findings, but no concrete number or trigger model (scheduled? on-demand? admin-invoked batch?) appears anywhere in the spec or addendum. This likely wants a similar shape to Stage 9's own deliberately-unscheduled batch jobs (`purge_expired_product_usage_events`/`refresh_product_usage_rollups`: callable, not auto-scheduled) but the actual trigger model is not assumed. Separately, "Platform Governance monitors... from approved platform reports" does not obviously map to any existing entity in this repository — no existing "platform report" table or endpoint was found. Both are real open questions, not implementation details — see §4 Q6 and Q7.

## 2. Work-package sequence (finalized against §4's confirmed decisions)

1. **WP10.1 — Schema: `AgentConfiguration` + `AgentFinding`.** Additive migration. `AgentConfiguration`: `id, logical_agent_name, scope_type ('platform'|'organization'), scope_id nullable (FK organizations, required iff scope_type='organization'), enabled, model_alias nullable (allowlisted, unresolved in v1 per §4 Q3 — no `llm_router.py` wiring), allowed_capabilities_json, updated_at`. `AgentFinding`: `id, agent_config_id (FK), severity, finding_type, entity_type, entity_id, summary, status, fingerprint, first_seen_at, last_seen_at, created_at, acknowledged_by/at, resolved_by/at, dismissed_by/at, superseded_by_id nullable, assignee/issue reference nullable`. Frozen `CheckConstraint` vocabulary per §4 Q2's accepted proposal — `finding_type` enum is **six** slugs only: `reviewer_coverage_gap, review_backlog_stale, icon_generation_missing, project_health_issue, symbol_set_health_issue, unresolved_reference` (Organization Steward) — `cross_tenant_authorization_failure` and `unresolved_governance_exception` are deliberately **omitted from the v1 `CheckConstraint`**, not included-but-unpopulated, since neither has a defined data source or meaning yet (§4 Q2 sub-answers); adding them is a follow-up additive migration once their prerequisites are separately resolved. `severity`: `low|medium|high|critical`. `status`: `open|acknowledged|dismissed|resolved|superseded`, with a partial-unique-index enforcing the one-active-finding-per-fingerprint rule. Deterministic fingerprint over `(capability_slug, scope_type, scope_id, finding_type, entity_type, entity_id, policy_version)`. Gated behind the already-existing `organization_agents_enabled` flag (§1.2) — no new flag needed.
2. **WP10.2 — Organization Steward: deterministic finding-generation service.** One service, callable on-demand only (§4 Q6 — no scheduler), computing the six in-scope finding types from existing tables (`OrganizationMembership`/`OrganizationMemberRole` for reviewer coverage, `PublicationSubmission`/review tables for backlog, icon/`generated_icon_seed` fields for icon status, `Project`/`SymbolSet`/`SymbolSetProject` for project/set health, `SymbolSetItem`/`CatalogFavourite` for unresolved references). Depends on WP10.1. Entirely deterministic (§4 Q4) — no LLM call anywhere in this package.
3. **WP10.3 — Platform Governance: deterministic finding-generation service.** Same shape, platform-scoped, reading only existing Platform Admin data (`Organization`, `PlatformRoleAssignment`) per §4 Q7 — `platform_admin_continuity_risk` (e.g. zero/near-zero active Platform Administrators) and `duplicate_organization_suspected` (name/code-similarity heuristic over existing `Organization` rows) only; the other two spec-named categories are the ones omitted per WP10.1. Depends on WP10.1.
4. **WP10.4 — Finding lifecycle API + escalation-routing seam.** Endpoints for listing findings (org-scoped and platform-scoped, mirroring the WP9.4 dual-route precedent) and for acknowledge/dismiss/resolve transitions with actor/timestamp recording (step-up required per I-25 "agent model/policy changes" — confirm at package start whether finding *resolution* itself needs step-up or only `AgentConfiguration` mutation does, since I-25's text names "agent model/policy changes" specifically). A `route_escalation(finding)` service-layer seam that records a durable, human-actionable escalation record — per §4 Q5, this does **not** call out to any live Hermes agent identity; it stops at "ready to be pointed at one." Depends on WP10.1-10.3.
5. **WP10.5 — Platform Admin `AgentConfiguration` management UI.** Enable/disable/scope a logical agent capability, view (not set, in v1 per §4 Q3) `model_alias`, step-up-gated per I-25. Depends on WP10.1.
6. **WP10.6 — Organization/Platform findings dashboard UI.** Severity, evidence, status, acknowledgement/dismissal/resolution actions, stale-snapshot indication. Depends on WP10.2-10.4.
7. **WP10.7 — F0.6 follow-up regression test (small, separately scoped).** Per §4 Q1's confirmed resolution: a small regression test asserting no manifest-consuming code path exists on `main` and that `SYMGOV_AGENT_RUNTIME` is the sole live worker-execution selector, closing the addendum's own literal bar ("one authoritative policy and a manifest-policy regression test") without reopening F0.6 as a Stage 10 blocker. Independent of WP10.1-10.6; can run in parallel.
8. **WP10.8 — Whole-stage audit.** Mirrors WP9.9 exactly: full regression suite (including the external/Postgres partition per the programme plan's own "run external workspace partitions because agent wiring changes" instruction), Contract Review, Security Review — with particular attention to FR-AGT-005/006/007 (no direct governance authority, tenant-scoped/permission-checked/auditable, human-required-to-execute) and to the two deliberately-omitted finding categories not silently reappearing.

This sequence was confirmed by Chris (2026-09-05) with a go-ahead to proceed through packages, flagging new design questions as they surface rather than pausing at every package boundary.

**WP10.2 implementation note (2026-09-05): DONE, not yet committed.**

- New service module `backend/symgov_backend/organization_steward.py` (`run_organization_steward(session, config, *, now=None)`), and shared plumbing `backend/symgov_backend/agent_finding_support.py` (`compute_fingerprint`, `upsert_active_finding`) reused by WP10.3. Trusts its caller to have already confirmed `config.enabled` and `scope_type == 'organization'` (raises `ValueError` if scope_type isn't organization) — the route layer (WP10.4) owns that gating, matching this repository's existing service/route separation convention.
- **Design sub-round confirmed this session, before writing detection logic:** of the six spec-named Organization Steward categories, four map onto clear, existing boolean/threshold-free signals with no invented numbers (`reviewer_coverage_gap`: zero active `symbol_reviewer`-capability members while any `OrganizationSymbolReviewSubmission` is active; `project_health_issue`: an active `Project` with no active `ProjectSymbolSet`; `symbol_set_health_issue`: an active `SymbolSet` with no `SymbolSetItem` in `availability_status='active'`; `unresolved_reference`: any `SymbolSetItem` with `availability_status='unavailable'`, a state this schema already tracks natively). Two needed Chris's confirmation: **`review_backlog_stale` uses a confirmed 14-day threshold** (an active `OrganizationSymbolReviewSubmission` with no decision after 14 days from `submitted_at`); **`icon_generation_missing` is deferred** (no data source exists — `Organization.fallback_icon_svg` is never null and no icon-generation-attempt/failure tracking exists anywhere), removed from WP10.1's `CheckConstraint` retroactively (both `schema.py` and the migration file, since neither had been committed yet) rather than shipped as an unreachable enum value.
- Findings are never auto-resolved by this service — a condition that stops being detected on a later run simply isn't re-touched; its `last_seen_at` falls behind, which is the "stale-snapshot detection" signal WP10.6's dashboard will read, not a reason for this module to change a finding's `status`. `policy_version="org_steward_v1"` versions the deterministic rule set itself, giving the "policy version" UI field (programme plan §16) a real value despite no model being invoked (§4 Q4).
- New test file `tests/test_wp102_organization_steward_postgresql.py` (10 cases, real disposable Postgres): a fully healthy organization produces no findings; each of the five finding types is independently proven to fire (and, where relevant, not fire when the condition doesn't hold — reviewer coverage, project health, review-backlog threshold boundary); idempotent re-run touches the same finding row's `last_seen_at`/`first_seen_at` rather than duplicating; and — proven against real Postgres, not by reasoning alone, per this repository's mandatory cross-tenant-isolation testing standard — running the Steward for one organization never creates or touches a finding under another organization's own `AgentConfiguration`.
- No test-fixture compatibility sweep needed (mirroring WP10.1's own note) — this package adds no wiring into any existing shared mutation/read function; `GovernedSymbol`/`SymbolRevision` rows in the new test file are constructed the same two-step way (`current_revision_id=None` then a later `UPDATE`) every real symbol-creation code path in this repository already uses, avoiding the circular-FK ordering problem that a naive single-insert construction would hit against real (non-deferred-FK) Postgres.
- Full portable backend suite re-run after this package: pending (background run in progress at the time this note was written; see the whole-stage audit or a later addendum for the confirmed count). WP10.1/WP10.2's own targeted Postgres suites (38 cases total across both new test files) are independently green.

**WP10.3 implementation note (2026-09-05): DONE, not yet committed.**

- New service module `backend/symgov_backend/platform_governance.py` (`run_platform_governance(session, config, *, now=None)`), reusing WP10.2's shared `agent_finding_support.py` plumbing. Raises `ValueError` if `config.scope_type != 'platform'`.
- `platform_admin_continuity_risk`: fires whenever fewer than two active `PlatformRoleAssignment(role='platform_admin')` rows exist. Zero is handled defensively (`severity='critical'`) but is unreachable in practice — this repository's own `enforce_platform_admin_eligibility` trigger already guarantees at least one active Platform Administrator at every commit; the realistic case this finding actually catches is exactly one (`severity='high'`, a single point of failure), which is not itself prevented by any existing invariant. `entity_type='platform'`, `entity_id` is the reserved `symgov` Organization's own id (the only stable anchor available, since `PlatformRoleAssignment` carries no organization scoping of its own).
- `duplicate_organization_suspected`: fires for every active `Organization` sharing another active organization's exact `name_key` (the same normalized-name field `organization_service.py` already soft-checks at creation/rename time, per `_normalize_name`) — a real, existing exact-match signal, not a fuzzy-matching threshold invented for this package. The earliest-created organization in each colliding group is left unflagged; every later one gets its own finding pointing back at the earliest.
- New test file `tests/test_wp103_platform_governance_postgresql.py` (5 cases, real disposable Postgres, function-scoped fixture rather than WP10.1/10.2's module-scoped one — platform-scoped facts like "how many active Platform Admins exist" are process-wide, so sharing one container across many test functions would make each test's count depend on test execution order): exactly-one-admin flags the risk, two admins is healthy, a duplicate `name_key` is flagged against the earlier organization, no duplicates is healthy, and an organization-scoped config is rejected. Building these fixtures surfaced two existing trigger invariants this package's tests must satisfy (not new constraints this package added): `enforce_platform_admin_eligibility` requires a Platform Administrator to also be an active `symgov`-organization admin, and `enforce_active_organization_admin_minimum` requires every active organization (not just `symgov`) to retain at least one active Organization Administrator at every commit — both existing precedents (`_make_platform_admin`'s own docstring) already documented this repository's fixture-writing convention for satisfying them.
