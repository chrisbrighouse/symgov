**Status:** Done, 2026-09-06. Programme plan §17 "Integrated verification" items 1-2:
*"Build a complete two-organization adversarial fixture with personal,
Organization User/Admin/reviewer, Platform Admin, inactive/suspended, and
API-key principals"* and *"Run route-policy inventory and tenant isolation
matrices for list/detail/search/count/asset/download/mutation endpoints."*

## Method

The route inventory below is generated from the live FastAPI route table
(`create_app().routes`, `/api/v1/*` surface only — the `/api/*` legacy
aliases mirror these 1:1 per `test_route_auth_enforcement.py`'s own
`test_workspace_policy_inventory_has_exact_surface_equivalence`, so they are
not re-listed), **161 unique method+path routes across 17 tag families**.

Stages 1–10 already built extensive tenant-isolation and route-policy
coverage; this audit's job is to confirm that coverage is real and
complete, cite it, and close any genuine gap — not to duplicate what
already passes. Every gap this audit found is closed by the new
consolidated fixture, `tests/test_stage11_wp11_3_adversarial_fixture.py`,
which provides every principal type named above (personal, Organization
User/Admin/reviewer-capability per organization, Platform Admin, an
inactive organization membership, and an API-key principal) in one place
rather than the ad hoc per-file fixture every prior stage test built.

Policy classes used below:

- **public** — no authentication required.
- **api-key** — Catalog API-key (`Authorization: Bearer …`) or session, catalog-scoped only.
- **authenticated** — any signed-in session (personal or organization).
- **org-member** — an active organization-session member (any base role).
- **org-admin** — organization-session member with `base_role="admin"`.
- **org-capability** — org-member plus a specific `OrganizationMemberCapability` (named per route).
- **platform-admin** — Symgov organization Admin with an active `PlatformRoleAssignment`.
- **workspace-reviewer / workspace-admin** — the internal agent-workspace role policy (`test_route_auth_enforcement.py`).

## Gaps found and closed

All five gaps below are closed by
`tests/test_stage11_wp11_3_adversarial_fixture.py` (13 tests, run against a
real disposable PostgreSQL container):

1. Symbol Set item mutation stays Organization-Admin-only even under the
   WP11.1 widened eligibility path — a non-admin `symbol_reviewer`-capability
   actor can browse (Stage 6, already tested) but must never write, own
   organization's symbol or not.
2. A plain Organization User (not just an Admin) gets 404 — not 403 — on
   another organization's Symbol Set by ID, items, and projects.
3. A Platform Admin's own organization-scoped session (bound to `symgov`)
   cannot reach another organization's org-scoped Symbol Set routes, while
   the same principal's actual platform-level cross-organization routes
   still work (positive control).
4. An inactive `OrganizationMembership` row resolves login to a
   zero-active-membership personal session (not a 401, and not binding into
   that organization) — proven at the real HTTP login/session layer, not
   only the service layer.
5. An API key genuinely authenticates the real API-key-gated
   `/catalog/symbols` route (confirmed: 401 with no `Authorization`
   header, rejected with an unknown bearer token) and never reaches any
   organization-scoped route (`/org/me`, `/org/me/symbol-sets`,
   `/org/me/projects`, `/organization-symbols`) — the latter for a
   structural reason (those routes authenticate only from the session
   cookie and never inspect `Authorization` at all), documented as such
   rather than implied to be API-key-specific discrimination logic. Together
   these prove the acceptance-checklist claim "API-key Catalog behavior
   remains public-only" (programme plan line 1052) at the route layer.

## What this audit deliberately does not re-do

Per §1.2 of the Stage 11 implementation plan, this package does not rebuild
already-passing per-stage tenant-isolation coverage. In particular the
`published`/`catalog` family already has four dedicated Postgres reader
matrices (WP8.1–8.7) and the `workspace` family already has an exhaustive
parametrized policy matrix (`test_route_auth_enforcement.py`) that is more
rigorous than anything this audit could add without duplicating it.
