## 2. Representative performance evidence (item 5)

**Decided (Stage 11 plan §4):** assume a roughly production-scale dataset
(a few thousand symbols across a handful of organizations) on whatever
hardware this session runs on; label results illustrative, never a
capacity guarantee.

`tests/test_stage11_wp11_5_performance_evidence_postgresql.py` seeds
1,500 approved organization-private symbols in one organization plus
1,500 published public symbols (3,000 total, one disposable Postgres
container) and:

1. Asserts `EXPLAIN` for the exact join
   `symbol_eligibility.eligible_organization_private_symbols` uses —
   the one WP11.1 introduced new call sites for (Symbol Set item list/
   replace/copy, `effective_palette`, `symbol_set_builder`) — shows no
   sequential scan on `governed_symbols` or
   `organization_symbol_review_decisions`. **This is the structural
   assertion that actually gates the test.** Corrected during WP11.6's
   independent review: the first draft asserted this against a SQL string
   hand-duplicated from the function's join shape, which could silently
   drift from the real query if the function were edited later without
   updating the duplicate in lockstep — it now captures the *actual*
   compiled statement the function executes (a `before_cursor_execute`
   event on the real engine call) and `EXPLAIN`s that instead. WP11.1 did
   not change this join's shape, only added call sites for it, and it
   reuses the indexes Stage 5/6 already built
   (`ix_governed_symbols_owner_visibility_organization_wide`,
   `ix_org_symbol_review_decisions_tenant_symbol_revision`,
   `ix_org_symbol_review_submissions_tenant_symbol_revision`).
2. Times two real HTTP endpoints against that dataset and prints the
   result (captured 2026-09-06, this session's disposable-container host):

   | Endpoint | Illustrative timing |
   |---|---|
   | `GET /org/me/symbol-sets/builder-search` (pageSize 50) | 1264.6 ms |
   | `GET /published/symbols` | 287.5 ms |

   The builder-search number is dominated by the **public** half of the
   search (`PUBLISHED_SYMBOLS_SQL`, unchanged Stage 6 code WP11.1 did not
   touch), not the organization-private eligibility join proven
   index-backed above — this disposable single-container environment has
   no connection pooling or warmed cache, so these numbers should be read
   as "did not regress catastrophically," not as a real P95 target. A
   generous, illustrative-only 10-second sanity bound is asserted so the
   test never gates a real release on this session's own hardware.

**Known pre-existing characteristic, surfaced by this evidence, not introduced
by Stage 11 (flagged by WP11.6's independent review):** the organization-private
half of Builder search (`symbol_set_builder._search_organization_symbols` →
`symbol_eligibility.eligible_organization_private_symbols`) has no
server-side row cap, unlike the public half's explicit
`PUBLIC_SEARCH_ROW_LIMIT = 500`; category/discipline filtering on that half
also happens in Python after the full per-organization result set is
fetched. This predates WP11.1 (the original Stage 6
`_search_organization_symbols` had the same shape) — WP11.1 only added
call sites and the category/discipline/format filters, it did not
introduce or remove any cap — but a growing organization's approved
private-symbol count now has a more reachable/attractive path to this
query via the new filters. Recorded here as a known, deferred scalability
item for a future stage to address (e.g. a matching row cap and
SQL-level filtering), not a Stage 11 regression and not fixed in this
package's own scope.

**Fail-closed, not fail-blocking, for advisory agents (item 5, second half):**
Organization Steward and Platform Governance are reachable only through
their own dedicated routes (`routes/agents.py` is the only route module
that imports either module — confirmed by repository search); no other
route depends on either module, so an authorization-dependency failure in
an agent run is structurally incapable of blocking any other core path.
Stage 10's own tests (`test_wp101`–`test_wp104_*_postgresql.py`) already
prove per-route behavior (404 on disabled flag, org-scoped isolation,
step-up requirements); this package adds the structural "cannot block
other routes" proof rather than re-testing what Stage 10 already covers.

## 3. Accessibility/responsive/copy/locale review (item 6)

Reviewed as a static code review (not a live browser pass) against the
WP11.1 UI diff — the only UI surface changed since Stage 10
(`frontend/src/SymbolSetBuilderPanel.js`'s new category/discipline/format
filters and `displayId` surfacing, `frontend/src/EffectivePalettePanel.js`'s
`displayId` surfacing):

- **Keyboard:** all three new filter fields are native `<input>` elements
  each paired with a `<label htmlFor>` — keyboard-operable and
  focusable by default, no custom click-only elements introduced.
- **Screen-reader semantics:** each filter input has an explicit
  `<label htmlFor>`. **Fixed during this review:** the wrapping filters
  `<div aria-label="Symbol Set Builder filters">` had no ARIA role, and a
  bare `<div>`'s implicit "generic" role does not support author-supplied
  naming per the ARIA spec — added `role="group"`, matching this same
  file's own existing convention for labeled control clusters (e.g. the
  "Reorder or remove …" and "Batch Symbol Set item actions" groups).
  `npm run test:frontend` re-confirmed 250 passed after the fix.
- **Focus states:** the new filter inputs are unstyled `<input>` elements
  with no custom class, identical in that respect to this file's
  pre-existing "Group"/"Preferred format" item fields — none of them are
  touched by `styles.css`'s outline-removal rules (those are scoped to
  specific classed selectors), so the browser's native visible focus
  indicator applies, unchanged from the surrounding code's own standard.
- **Responsive viewport:** the new filters wrapper uses a class
  (`.symbol-set-builder-filters`) with no dedicated stylesheet rule, so it
  falls back to normal inline flow (bare `<label>` elements are
  `display: inline` by default) — the same no-dedicated-CSS baseline this
  file's pre-existing per-item "Group"/"Preferred format" labels already
  use, so there is no new responsive-layout risk relative to the
  surrounding code.
- **American-English copy:** "Category," "Discipline," "Format,"
  "Approved organization symbol" — all American-English spelling,
  consistent with the rest of the file. (Correction, 2026-09-06: an
  earlier draft of this note also listed "Clear filters" — the stale
  `symgov-stage6-fixes` worktree had a Clear-filters button, but WP11.1
  deliberately did not port it, and no such control exists in the shipped
  `SymbolSetBuilderPanel.js`. Caught by WP11.6's independent review;
  corrected here rather than left as an inaccurate evidence claim.)
- **Locale-aware date/number formatting:** not applicable — `displayId`/
  `catalogSymbolId` are opaque identifier strings, not locale-formatted
  dates or numbers, and WP11.1 introduced no new date/number displays.
