## Lane 1 — Spec compliance: PASS WITH NOTES (corrected)

The core WP11.1 loosening was confirmed faithful to the programme-plan-line-1072
widened definition: every eligibility call site derives `organization_id`
exclusively from the authenticated caller's own session
(`principal.organization.id`, itself traced to
`stage4_authorization.require_stage4_principal`'s cookie-bound lookup) —
never from a request parameter. No DB-level constraint ever restricted
`SymbolSetItem` to public symbols, so no migration was needed. I-08/I-23/I-24/I-25
all still hold as implemented; no scope creep beyond same-organization found.

**Findings and corrections:**

1. **Medium — fabricated evidence claim, corrected.** The WP11.5 evidence
   doc's accessibility section originally listed "Clear filters" among the
   reviewed copy strings — no such control exists in the shipped
   `SymbolSetBuilderPanel.js` (it existed only in the stale worktree
   version WP11.1 deliberately did not port). Corrected in
   `docs/plans/2026-09-06-stage11-wp11.5-regression-performance-accessibility-evidence.md`
   with an explicit correction note rather than a silent edit.
2. **Medium — WP11.3's API-key acceptance-checklist citation didn't match
   what its cited test actually proved, corrected.** See Lane 2 finding 1
   below for the full trace and fix.
3. **Low/Info, pre-existing, no action needed.** The Stage 6 plan's own
   WP6.4 note claimed `SymbolSetItem` "structurally cannot reference an
   organization-private symbol" — this was already only an app-level
   invariant, not a DB one, which is presumably why WP11.1 could loosen it
   with zero migration. Predates Stage 11; `effective_palette.py`'s
   docstring already only claims code-level (not DB-level) invariants.

## Lane 2 — Security/code-quality: PASS WITH NOTES (corrected)

**No cross-organization data leak, SQL injection, ReDoS, or ETag bypass
found.** Specific findings:

1. **Medium, corrected — the WP11.3 "API-key principal" tests didn't test
   what their names claimed.** The reviewing agent traced
   `stage4_authorization.require_stage4_principal` and confirmed
   organization-scoped routes authenticate *only* from the session cookie
   and never inspect the `Authorization` header — so
   `test_api_key_principal_is_rejected_by_every_organization_scoped_route`
   passed for a purely structural reason (no session cookie), not because
   of any API-key-specific check, and would have passed identically with
   the header removed entirely. This session independently verified that
   claim by reading `stage4_authorization.py` directly. The review agent's
   *separate* claim that the positive-control test
   (`/api/v1/catalog/symbols`) "doesn't consult `CatalogApiKey` at all...
   fully public" was checked and found **incorrect** — an empirical probe
   (`TestClient` with no `Authorization` header → 401; with an unknown
   bearer token → rejected by the same key lookup) confirms that route
   genuinely requires a valid `CatalogApiKey` via
   `catalog_api_auth.require_catalog_scope`. **Fix applied:** renamed and
   re-documented both tests in
   `tests/test_stage11_wp11_3_adversarial_fixture.py` (now
   `test_a_session_less_api_key_client_never_reaches_any_organization_scoped_route`
   and
   `test_the_seeded_api_key_actually_authenticates_the_catalog_route_it_is_scoped_for`)
   to state accurately which one is structural and which one genuinely
   exercises the `CatalogApiKey` row the fixture creates. Updated the
   WP11.3 route-policy matrix and the Stage 11 plan's own summary to match.
   All 13 tests in that file re-run green after the fix.
2. **Low/Medium, documented as a known pre-existing item, not fixed in
   this package's scope** — the organization-private half of Builder
   search has no server-side row cap (unlike the public half's
   `PUBLIC_SEARCH_ROW_LIMIT = 500`), predating WP11.1. Recorded in the
   WP11.5 evidence doc as a deferred scalability item for a future stage.
3. **Low, corrected** — the WP11.5 performance test originally asserted
   index usage against a SQL string hand-duplicated from
   `eligible_organization_private_symbols`'s join shape, which could drift
   from the real query if the function changed without updating the
   duplicate in lockstep. **Fix applied:** rewrote
   `tests/test_stage11_wp11_5_performance_evidence_postgresql.py` to
   capture the actual compiled statement via a `before_cursor_execute`
   SQLAlchemy event during a real call to the function, and `EXPLAIN`
   that instead. Re-run green (illustrative timings changed slightly as a
   result of the re-run, not the fix: builder-search 1264.6 ms,
   published-symbols-list 287.5 ms — both updated in the WP11.5 doc).
4. No SQL injection, no ReDoS, no ETag/concurrency bypass, no dead code —
   all independently confirmed by direct code reading (subprocess
   list-form args, bound `:param` placeholders throughout, non-ambiguous
   regex quantifiers, row-locked `replace_items` serializing concurrent
   writers before the etag comparison).
