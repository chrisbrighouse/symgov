## What was genuinely missing — closed by this package

None of the above rehearses **the whole chain in one continuous motion**:
restoring from the true pre-organization production revision and upgrading
straight through every one of the ~19 migrations to the current head on
one database, confirming a legacy dataset survives that entire jump, then
building the bootstrapped Symgov organization and two real tenant
organizations *on that same continuously-migrated database* — and proving
the visibility-floor rollback discipline still holds once that whole
accumulated, realistic dataset exists (not one stage's own minimal
fixture).

`tests/test_stage11_wp11_7_migration_rehearsal_postgresql.py` — six tests,
run in sequence against one continuously-evolving disposable database
(`test_a` through `test_f`, module-scoped):

- **test_a** — restores to `20260802_0026` (the revision immediately
  before Organization Stage 1's `20260808_0027`), confirms `governed_symbols`
  has no organization-related columns yet, seeds a legacy owner, a legacy
  personal user, and 5 ownerless public symbols, inventories user/symbol
  counts, then upgrades in one motion straight to `20260905_0044` (current
  head). Re-verifies: counts unchanged, both legacy users still active,
  all 5 legacy symbols present with `owner_organization_id IS NULL`,
  `visibility = 'public'`, `organization_wide = false` — i.e. landed
  exactly ownerless-public-equivalent under the new columns, never
  silently reassigned to an organization or made private.
- **test_b** — bootstrap dry-run (`apply=False`) commits nothing (0 rows
  in `organizations` afterward); apply (`apply=True`) creates exactly one
  protected, active `symgov` organization; a second apply is idempotent
  (no duplicate, no error) — against the same database test_a left at head.
- **test_c** — seeds two real tenant organizations (via the same
  `_add_membership`/`_create_user_with_global_roles` helpers WP11.3/WP11.4
  use) on that same database (which now also carries the legacy dataset
  and the bootstrapped Symgov organization from test_a/test_b, not a clean
  fixture) and confirms a direct membership-table query finds zero
  cross-tenant membership rows.
- **test_d** — its own separate, genuinely zero-private-rows disposable
  database: upgrades to head, downgrades all the way back to the
  pre-organization revision (schema-first pre-floor rollback, flags off,
  zero private rows — confirmed clean), then upgrades back to head
  (downgrade-then-upgrade proof, before any tenant data exists).
- **test_e** — back on the accumulated database from test_a–test_c:
  confirms zero `organization_private` rows exist yet (this rehearsal's
  own dataset never created one — that exact guard-under-real-data proof
  is `test_wp76`'s job, cited above, not repeated here), then rehearses
  rollback discipline on top of unrelated accumulated Stage 1-10 data
  (organizations, memberships, a bootstrapped Symgov org): the schema
  downgrade succeeds (as expected with zero Stage 5 rows), lands the
  Alembic version table at exactly the requested revision (no partial/stuck
  state), and re-upgrades back to head cleanly. This proves the Stage
  5 guard's emptiness check is specific to Stage 5's own tables — neither
  falsely tripped nor silently bypassed by unrelated accumulated data.
- **test_f** — single-Alembic-head re-confirmed directly (`ScriptDirectory.get_heads()`),
  plus a referential-integrity spot-check on the actual accumulated
  database: zero orphaned `organization_memberships` rows, zero
  `governed_symbols` rows referencing a nonexistent organization.

## Emergency pre-floor recovery ordering — procedural, not code-testable from this repository

Programme plan §17's required ordering (external denial of every public
Catalog/published/page/package/download/asset/alias/Favorite route, then
stop/drain of all web/API/Hannah/Whitney/other readers, before starting
an older pre-floor backend; never reopen/resume until an at-or-above-floor
release is restored and verified) is a **deployment-topology** procedure,
not an internal feature-flag gate this repository can flip and assert
against. The `published`/Catalog routes are not behind any
`organizations_enabled`-style flag at all (they predate organizations
entirely and are meant to stay always-on for legitimate traffic) — the
"deny at the external ingress" step is necessarily an nginx/load-balancer/
Compose-level action outside this repository, consistent with the
already-established boundary ("Production topology is externally managed
and the repository does not prove the currently deployed release,"
programme plan line 1033, and this stage's own §1.1 baseline note). This
package records the required ordering as a checklist for whoever executes
an actual emergency recovery, rather than fabricating a code path that
would only simulate — not prove — an external-ingress/reader-topology
action this repository has no authority over.

## Redaction

No disposable container's connection string or password appears in this
document or in test output beyond the same fixed, non-secret placeholder
pattern every other `*_postgresql.py` test in this repository already
uses (`disposable-<name>-password`, torn down with the container at test
end). All seeded identities use synthetic `@example.test` emails except
the one hardcoded `PROTECTED_OWNER_EMAIL` application constant, which is
not a live credential.

## Regression note

Re-running the cited pre-existing tests individually alongside the new
WP11.7 file surfaced one apparent failure
(`test_wp1_populated_database_refuses_guarded_downgrade_and_keeps_revision`)
that turned out to be a test-selection ordering artifact — module-scoped
Postgres-container fixtures interacting across an arbitrary multi-file
`pytest` selection, not a real regression. Re-running
`tests/test_project_symbol_set_postgresql.py` as its own complete file
(the correct, supported invocation) showed that same test passing, with
only the one already-documented pre-existing baseline failure
(`test_public_eligibility_rejects_revision_owned_by_a_different_symbol`,
confirmed present on unmodified `origin/main` since WP11.1) — no new
regression introduced by this package.
