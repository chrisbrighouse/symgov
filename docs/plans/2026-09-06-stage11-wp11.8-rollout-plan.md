## The 10 steps

### 1. Back up database and object storage; verify restore command in disposable environment

- Take a full backup of the production database and the object-storage
  bucket(s) backing icon/asset delivery, using whatever mechanism the
  hosting environment already provides (this repository does not own or
  document that mechanism — it is externally managed, per §1.1).
- Before trusting the backup, restore it into a disposable environment
  and confirm the restore actually completes and the database is queryable
  at the expected Alembic head. WP11.7's disposable-Postgres harness
  (`tests/test_stage11_wp11_7_migration_rehearsal_postgresql.py` and the
  `_database()`/`_alembic()` pattern it and every other `*_postgresql.py`
  test file share) is the mechanism to reuse for this restore-verification
  rehearsal — it is not itself the production backup/restore tool.

### 2. Deploy migrations/additive backend with all organization flags off

- Deploy the backend at commit `22c3ad3` (or whatever later commit this
  plan is re-authorized against at execution time — re-confirm the exact
  commit before running this step).
- Run `alembic upgrade 20260905_0044` (the sole current head, confirmed by
  `tests/test_public_projection_migration.py::test_new_migration_is_the_sole_alembic_head`
  and WP11.7's own `test_f_single_alembic_head_and_no_orphaned_organization_references`)
  against the real production database.
- Every organization-related flag must be off at this point (the actual
  code default, `backend/symgov_backend/settings.py:145-186`, unless an
  environment already has one or more of these already set — re-verify,
  do not assume): `SYMGOV_ORGANIZATIONS_ENABLED`,
  `SYMGOV_ORGANIZATION_ADMIN_ENABLED`,
  `SYMGOV_ORGANIZATION_CUSTOM_ICONS_ENABLED`,
  `SYMGOV_ORGANIZATION_ICON_UPLOAD_ENABLED`,
  `SYMGOV_PLATFORM_ADMIN_ENABLED`, `SYMGOV_SYMBOL_SETS_ENABLED`,
  `SYMGOV_ORGANIZATION_SYMBOLS_ENABLED`,
  `SYMGOV_ORGANIZATION_AGENTS_ENABLED`. The migration itself is additive
  only (WP11.7 confirmed the whole chain preserves legacy ownerless public
  symbols and personal accounts unchanged) — with flags off, the deployed
  backend continues serving exactly its pre-organization behavior.
- Icon upload stays disabled regardless of the flag above, per the
  Stage 3 deferred item (malware scan not integrated) carried forward
  through every stage's own kickoff prompt — do not enable
  `SYMGOV_ORGANIZATION_ICON_UPLOAD_ENABLED` at this step or any later step
  in this plan without a separate, explicit decision to close that gap first.

### 3. Run read-only inventory and reviewed Symgov bootstrap; apply only with explicit authorization

- Read-only inventory first: confirm user/public-symbol counts and
  canonical IDs match what backup/restore verification (step 1) recorded,
  against the real production database, with `SYMGOV_ORGANIZATIONS_ENABLED`
  still off.
- Dry-run the bootstrap (from `backend/`, or with it on `PYTHONPATH`;
  confirmed working with this exact invocation, 2026-09-07):
  `python3 -m symgov_backend.management bootstrap-symgov-organization`
  (no `--apply`) — reviews what it *would* do (create the protected
  `symgov` organization) without committing. `reconcile_symgov_organization_bootstrap`
  (`backend/symgov_backend/organization_service.py:330`) requires an
  active protected-owner account
  (`chris.brighouse@hotmail.co.uk`) to already exist and be active before
  `apply=True` is accepted — confirm that account's live status first.
- **Apply only with Chris's separate, explicit authorization at execution
  time**: `python3 -m symgov_backend.management bootstrap-symgov-organization --apply`.
  WP11.7 proved this is idempotent (a second apply makes no further
  change) and creates exactly one protected, active `symgov` organization
  — but idempotency is not authorization; still require an explicit
  go-ahead for the real apply.

### 4. Deploy frontend hidden behind flags

- Deploy the built frontend (`npm run build`, or `build:isolated` — never
  `build:publish`/`publish:static` without Chris's separate explicit
  approval, per `CLAUDE.md`) to the environment that serves it.
- With `SYMGOV_ORGANIZATIONS_ENABLED` (and the other organization flags)
  still off, the frontend's own capability negotiation
  (`GET /api/v1/auth/me`'s `capabilities` object —
  `organizationsEnabled`/`organizationAdminEnabled`/`platformAdminEnabled`/
  `symbolSetsEnabled`/`organizationSymbolsEnabled`/`organizationAgentsEnabled`/
  `organizationIconUploadEnabled`, all `false`) means every
  organization-aware UI surface (Symbol Set Builder, effective palette,
  organization admin pages, platform admin pages) stays hidden from
  navigation even though the code is live — this is the "hidden behind
  flags" property, not a separate frontend-side flag file to maintain.

### 5. Enable the backend pilot allowlist for the active `symgov` organization only

- Set `SYMGOV_ORGANIZATION_PILOT_CODES=symgov` (the only pilot code — the
  reserved, protected organization created in step 3) and turn on
  `SYMGOV_ORGANIZATIONS_ENABLED` (and whichever of the other organization
  flags this pilot actually needs — at minimum
  `SYMGOV_ORGANIZATION_ADMIN_ENABLED`, `SYMGOV_SYMBOL_SETS_ENABLED`,
  `SYMGOV_ORGANIZATION_SYMBOLS_ENABLED` for the pilot to exercise Symbol
  Sets/organization symbols; `SYMGOV_PLATFORM_ADMIN_ENABLED` only once
  Ed's platform-admin binding, handled outside this repository, is ready).
  Pilot-code grammar is enforced at settings-load time
  (`backend/symgov_backend/settings.py:27-40`,
  `NORMALIZED_ORGANIZATION_CODE_PATTERN`) — a malformed value fails closed
  at startup rather than silently admitting an unintended organization.
- Active pilot-organization membership and effective role/capability are
  the *only* restriction — there is no separate undocumented named-user
  allowlist (programme plan line 1026). Confirm this by reading
  `backend/symgov_backend/stage4_authorization.py:88` and
  `backend/symgov_backend/organization_authorization.py:28` at execution
  time, not just trusting this note, in case either has changed since
  this plan was drafted.
- **Verify `/auth/me` capability negotiation before exposing UI
  navigation**: log in as a real `symgov`-organization member against the
  now-enabled backend and confirm `GET /api/v1/auth/me`'s `capabilities`
  object now reflects the enabled flags, and that `user.session.activeOrganizationId`
  resolves to the `symgov` organization for that member — before
  announcing the pilot is live to anyone.

### 6. Smoke test

Run each of the following against the real, now-partially-enabled
production environment (all as the `symgov` pilot organization, using a
real pilot account — not the disposable Postgres rehearsal, which already
covered the migration/bootstrap slice of this in WP11.7):

- **Login/session**: `POST /api/v1/auth/login`, `GET /api/v1/auth/me`,
  organization-selection challenge if the pilot account holds more than
  one membership, forced PIN change if `mustChangePin` is set.
- **Admin**: `GET /api/v1/org/me`, `GET /api/v1/org/me/members` as an
  Organization Admin.
- **Project/set**: create a Project, create a Symbol Set, activate it,
  make it available to the Project, confirm `GET /api/v1/org/me/symbol-context`
  resolves it as the active set.
- **Private symbol**: create an organization-private draft
  (`POST /api/v1/organization-symbols`), submit for review, decide
  (approve) through the real review-decision route, confirm it becomes
  eligible for the Symbol Set Builder (`GET /org/me/symbol-sets/builder-search`)
  and, per WP11.1's widened path, addable as a direct Symbol Set item.
- **Catalog**: `GET /api/v1/published/symbols`,
  `GET /api/v1/published/packs`, confirm the pilot organization's private
  symbols never appear there (Public Catalog stays independently
  browseable, unaffected by the pilot).
- **Audit**: confirm an `audit_events` row was written for at least one of
  the mutations above (project/set creation, review decision).
- **Queue**: confirm the existing Workspace agent-queue routes
  (`GET /api/v1/workspace/agent-queue-items`,
  `GET /api/v1/workspace/agent-worker-health`) are unaffected and still
  green — this pilot must not have touched the pre-existing
  agent-workspace surface at all.
- **Email**: trigger at least one email-producing action (e.g. a forced
  PIN reset, if applicable to the pilot account) and confirm a row lands
  in `email_outbox`.
- **Liveness/readiness**: `GET /api/v1/health` returns `ok: true`. (This
  repository has one combined health endpoint, not separate liveness and
  readiness probes — if the hosting environment's own deployment
  configuration expects two distinct probes, confirm out-of-band how it
  is actually wired; that wiring is external to this repository.)
- **Rollback**: confirm the rollback procedure (step 8 below) has actually
  been rehearsed — not merely written down — before treating the smoke
  test as complete.

### 8. Rollback procedure

- First rollback action: **disable flags** (set every organization flag
  from step 5 back to off) and deploy only a release at or above the
  Stage 5 visibility floor (Alembic revision `20260829_0033` or later —
  never a release below it once any organization-private/organization-wide
  data exists, per WP11.7's `test_e_rollback_past_the_visibility_floor_is_refused_...`
  and the DB-level guard in `20260829_0033`'s own `downgrade()`, which
  raises `cannot downgrade organization symbol visibility while Stage 5
  data exists` if you try). Then roll forward once the underlying issue
  is fixed.
- **Do not drop used tenant data in production** and **do not revert
  readers below the visibility floor** once private semantics/data
  exists. This is not an ordinary migration-rollback path — WP11.7's
  rehearsal proves the schema-first pre-floor rollback is only safe with
  zero private rows (its `test_d`); once real tenant data exists, "roll
  back" means disable-flags-and-redeploy-at-or-above-floor, never a
  schema downgrade below the floor.

### 9. Emergency pre-floor recovery ordering

If an emergency absolutely requires running a pre-floor backend (a
release below Alembic revision `20260829_0033`) after private/organization-wide
data already exists — this should be a last resort, not a routine
rollback path:

1. First, **deny at the external ingress** every public
   Catalog/published/page/package/download/asset/alias/Favourite route
   (`/published/*`, `/catalog/symbols*`, `/catalog/*` reads). This is an
   nginx/load-balancer/Compose-level action outside this repository —
   confirmed in WP11.7 that no internal feature flag exists to gate these
   routes (they predate organizations and are meant to stay always-on
   under normal operation), so this step is necessarily external.
2. Then **stop and drain every web/API and background reader**,
   explicitly including Hannah and Whitney (and every other
   agent-workspace reader under `/workspace/*`).
3. Only after both of the above are confirmed complete, start the older
   pre-floor backend.
4. Keep those routes denied and readers stopped. **Never reopen or resume
   them** until a release at or above the visibility floor is restored
   and the complete visibility/demoted-revision/multi-symbol-pack/count/
   alias/asset/Favourite/Hannah/Whitney checks all pass again.

### 10. Keep the legacy protected-owner safeguard until a separately reviewed cutover

- The protected-owner safeguard (the hardcoded `chris.brighouse@hotmail.co.uk`
  account, its perpetual-Plus/Admin repair, and its exemption from
  cancellation/deactivation/soft-deletion/Admin-stripping — documented in
  `backend/README.md`'s "User subscriptions and privileged roles" section)
  stays in place through this entire rollout. Do not retire it
  automatically as part of enabling organizations.
- Retiring it requires a **separate, later, reviewed cutover** that
  specifically proves: the reserved `symgov` organization's own
  continuity guarantee (`enforce_platform_admin_eligibility` — at least
  one active Platform Administrator at all times, DB-trigger-enforced),
  eligible-Platform-Admin continuity more broadly, step-up-authentication
  behavior, account-recovery behavior, and rollback behavior all still
  hold without the legacy hardcoded safeguard. That cutover is out of
  this plan's scope — this step is only "keep it," not "plan its removal."
