## 3. Corpus, index, approval and retrieval contracts

**Draft input:** an exact-path reviewed inventory based on `SourceInventory` (`ed_knowledge_sources.py:44-80`) plus separately curated `KnowledgeManifest` claims (`ed_knowledge.py:66-143`). Represent approved ranges and rights disposition alongside source SHA-256 and commit in a new strict Stage 4 build schema; do not mutate the Stage 1 example to impersonate approved production knowledge. One document may contain multiple claims; every claim must have a nonempty citation span or reviewed symbol and the same source path/version/topic as its parent (the existing validator only checks topic; add the missing invariants). Reject duplicate IDs globally, contradictory active versions for the same fact key, nonreciprocal/broken supersession, cycles, invalid range/symbol, unsupported visibility, and unexpected source drift. The example manifest's `published` records are test fixtures, **not** a runtime approval receipt.

**Draft output contract (proposed v1, new schema):** `manifest.json` (schema/index versions, source allowlist with byte hashes/commit, build timestamp, status `draft`, coverage and exclusions, deterministic index digest), `chunks.jsonl` (one curated claim per chunk in first slice; stable claim ID plus source path/version, line range or symbol, topic, visibility, approval, extracted-at, title, short vetted text, supersession and explicit scope), `postings.json` (normalized term -> sorted distinct chunk IDs and frequencies), `build-report.json` (bounded safe errors/warnings and incomplete topics). Fixed UTF-8, canonical JSON keys/line endings, sorted source/claim/posting order; index digest hashes canonical `chunks.jsonl` + `postings.json`, manifest digest hashes the canonical manifest bytes separately to avoid a self-referential hash. An explicit `--extracted-at` UTC value or pinned `SOURCE_DATE_EPOCH` and pinned source commit make repeated local builds byte-identical. Bound source-file bytes, unit size, total chunks, term count, index bytes and error count before allocation; define concrete limits in RED tests and document them in the eventual runbook. Split overlong reviewed Markdown claims by line-preserving subrange only after reapproval; never silently truncate evidence, line ranges or secret-bearing content. Whole-module extractor units are *discovery only*, not final chunks.

**Approval:** offline builder writes **draft only** to a new empty staging directory outside live serving paths. Steward (Chris initially: spec §10.6, `...spec.md:327-329`) reviews exact paths, rights, source hashes, individual claim text/spans, topic coverage, exclusions, postings/query fixtures and manifest/index SHA-256. A separate, authenticated and audited release procedure records steward identity, timestamp, reviewed manifest+index hashes and approval decision; copy the exact reviewed bytes to an immutable approved release artifact without rewriting claims, timestamps or digest. No developer flag or build success may convert draft to published. At runtime accept only approved, hash-matched published claims; `organization` claims require an explicit bound organization scope and eligibility check, never a bare `visibility=organization` shared across tenants. First corpus should contain only `authenticated` public-product explanations; reject `organization` and `internal` from user retrieval until a reviewed scope model exists. Superseded/retired records remain available to operators for audit but never rank for users. No filesystem promotion or runtime load is authorized now.

**Lexical retrieval first:** normalize Unicode cautiously (NFKC + casefold) and tokenise bounded question/claim title/text; index exact terms and optionally a reviewed small alias map (`ICS`, `symbol set`), never query live tenant data from this index. Score deterministic weighted title/exact-phrase/term-frequency matches; ties break by stable chunk ID. Limit input to existing 1,000-char request bound, return at most 4 chunks and 4,000 vetted context characters, with a fixed maximum postings scan and timeout/fail-closed policy. Zero eligible results, all stale results, malformed index or absent approval yields `cannot_answer`/documentary-evidence-unavailable; do not ask the LLM to improvise a `knowledge` answer with no approved citation. Version `knowledgeVersion` against the approved manifest digest. Retrieval returns opaque `knowledge:<version>:<chunk-id>` reference, safe title, source version, optional safe line locator, and internal source path for server-only audit; UI-facing citations must expose a friendly label/version, not raw `backend/...` paths (spec §10.5). Keep `EdCitation`/`EdChatResponse` bounds (`schemas.py:1997-2029`) and add only necessary backward-compatible fields for safe version/detail. The server assembles citations from retrieved items, never from provider-supplied strings; verify material claims against offered references and reject fabricated citation IDs. For mixed questions retrieve knowledge *and* call the same Stage 3 typed read tools; live `asOf` is not a corpus `sourceVersion`. Prompt treats source text as untrusted data; no instructions from retrieved material can override Ed policy. Leave the existing Catalog Ed and `/llm/chat` meanings untouched.

**Staleness:** before draft build and before runtime load, verify each source's current bytes against pinned SHA-256 and file/range/symbol; refuse changed, missing, symlinked or unsupported sources. At release, pin corpus to matching reviewed source snapshot; if serving from an immutable release tree, validate against that tree, not a mutable developer checkout. Failure means no corpus answers (and a bounded diagnostic/alert), not silent reuse of stale claims or unversioned web fallback. A live read tool may still answer its own authorized current-state question without claiming that the corpus is current. If no approved snapshot has ever existed, return the Stage 3 warning/no-answer path until integration is deliberately activated; don't report the example fixture as approved knowledge.

## 9. Review corrections to slices A–C (2026-09-29)

Chris accepted the Claude review of the unchanged A–C candidate (hashes as in the Hermes handoff, `ed_corpus.py` `e5c2f7e6…`) as the formal combined Contract+Security review. The review found the following, and each correction below was made test-first. These correct the proposed contract in §3; where §3 disagrees, this section governs.

1. **Approval is bundle-level only.** §3 listed `approval` among the chunk fields. As built, every chunk said `draft`, retrieval served only `published`, and approval copies bytes unchanged, so an approved bundle could never answer; flipping the field and recomputing the unkeyed digests passed `verify`. Chunks now carry no approval state, and a chunk that does is malformed. `query_index` requires `approved_index_digest` and serves nothing unless it equals the digest of the exact chunk and postings bytes. Establishing that a digest was really approved is the steward record's job (decision §7.2), and is not implemented.
2. **Locators are resolved once.** The builder accepted a Markdown heading slug (`guide`). Retrieval and `verify` then looked for it verbatim and case-sensitively in `# Guide`, treated the chunk as drifted, and failed the whole query. The builder now resolves a heading or symbol to its unit's exact line range, which bounds it by the unit limit and refuses ambiguous names. Chunks always carry the range; retrieval and `verify` check range and hash only, and the symbol is a display label. A new test builds a bundle and queries it end to end.
3. **The credential check targets material, not names.** It rejected `token = request.cookies.get(...)`, which dropped four of the fifteen §2 candidates (`stage4_authorization.py`, `dependencies.py`, `ed_read_tools.py`, `OrganizationSelectionPage.js`). Across all 570 tracked source and docs files it now flags four, and each is a quoted literal or a documented example key.
4. **Supersession survives the build.** Chunks now carry `supersededBy`, which retrieval already checked but the builder never wrote.
5. **Retrieval can say it has no answer.** Stop words are removed from postings and questions, so function words no longer match every chunk. A long question within the 1,000-character request bound is capped at 128 distinct terms rather than reported unavailable.
6. **Model context is labelled.** Each passage is prefixed with its `knowledge:<version>:<chunk>` reference and title, and the 4,000-character budget counts the labels.
7. **One file can back several reviewed ranges.** The Stage 1 inventory rejected a second entry for the same path, and the builder keyed sources by path, so one file could serve only one range and one topic. An entry is now identified by its path plus its range and symbol. Entries for the same file must pin the same hash and kind, and repeating the same locator is a duplicate.
8. **Extraction no longer crashes on long identifiers.** A long entry ID plus a long Markdown heading slug overflowed the 128-character unit ID. The CLI then died with a traceback. Such IDs now fall back to a stable digest form, and an unexpected validation error during a build is reported as a bounded `build_failed`.
